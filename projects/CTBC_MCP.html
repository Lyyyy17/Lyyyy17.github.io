CTBC Bank — Agent × MCP Payment Advisor

Fintech · CTBC Internship Team Project · Python, FastMCP, Claude API, React, Render · Architecture v8.1

Credit-card rewards are scattered across fine print, so choosing which card to swipe is a real decision cost. Our team built a payment recommendation service on the Claude × Model Context Protocol (MCP) architecture: the LLM interprets a natural-language spending scenario ("buying a NT$5,000 haul at Costco"), but every reward calculation runs in a deterministic, bank-owned backend. The service is live on Render with a public /mcp endpoint — any remote-MCP client, such as Cursor, can connect and use the recommendation tools directly, no clone or API key required.

Problem

Card benefits change constantly, differ by channel, and come with caps and conditions. Existing tools are static comparison tables or scripted chatbots that can't answer situational questions. A user who already knows what they're about to buy just wants one answer: which of my cards earns the most here?

Why MCP (Not Just Function Calling)

Pure function calling can handle tool invocation, but when card rules change it produces unstable recommendations (the LLM reasons about rewards directly), is hard to maintain, and can't share tools across applications. MCP fixes the division of labor: the LLM understands the user and picks tools; the backend owns the truth.

  • Reliable numbers: reward logic, card data, and constraints live in the MCP server, not in the prompt. Tools only read from validated card data (merged_cards.json), the channel mapping table, and backend calculation logic — the LLM never invents a card, promo, or cashback rate.
  • Reusable interface: the same /mcp serves the web demo, Claude MCP Connector, Cursor, or a bank's future channels (mobile banking, customer-service tools) — no per-client function schemas to rewrite.
  • Permission boundary: the user's selected card list (cards_owned) is a hard constraint. It is written into the chat system prompt to restrict Claude's tool calls, re-validated against canonical card data on the backend, and used directly by the deterministic REST/SSE flow — so the agent can only recommend cards the user actually holds, and the same boundary maps cleanly onto a future bank login session.
  • Rules stay bank-owned: ranking logic, promo conditions, data updates, and fallback rules are maintained in the controlled service; prompts only guide when to call tools, never what the numbers are.

How It Works

  • Flow: user selects held cards → describes the purchase in natural language → the agent parses intent and channel → calls MCP tools → backend computes and ranks rewards → returns top cards with reasons.
  • Two modes: a standard recommendation mode streaming structured SSE for fast deterministic results, and an Agent mode where Claude calls /mcp through the real MCP Connector — the UI surfaces each tool use and tool result, making the agent's reasoning transparent instead of a black box.
  • MCP tools: recommend_payment (parse scenario → full recommendation), search_by_channel, compare_cards, get_promotions, get_card_details, list_all_cards, plus MCP Resources exposing per-card JSON (card://ctbc/{card_id}) and the channel taxonomy.
  • Recommendation logic: (1) normalize free-text merchants into 17 standard channels, with a general-spending fallback that extracts merchant keywords when no channel matches; (2) two-layer search — limited-time promotions first, then each card's base channel rewards, with the fallback rate explicitly labeled as a floor; (3) compute spend × reward rate, always capped against the card's reward ceiling, and rank a Top 3 by both estimated reward and reward rate.
  • Architecture: React front end; Starlette + uvicorn on Render serving REST, structured SSE, and FastMCP's /mcp Streamable HTTP from one ASGI service; card data covers 6 CTBC co-branded cards plus 7 non-CTBC cards included as benchmark data for cross-bank recommendation logic.

Try It from Any MCP Client

The endpoint is public — point Cursor (or any client supporting remote MCP over Streamable HTTP) at:

https://ctbc-payment-advisor.onrender.com/mcp

Then ask something like "用 ctbc-payment-advisor 比較 LINE Pay卡和 momo聯名卡， 在 momo 消費 3000 元哪張比較划算" — your own agent does the reasoning; this service supplies the card data, reward math, and rankings.

Engineering Practice

  • Tested like a product: pytest covers recommendation logic, data contracts, MCP tool results, and the SSE contract; Playwright covers web E2E; CI runs on every push (Node 22 / uv toolchain).
  • Data integrity: the card runtime schema is versioned (card_schema.json), scraped bank data passes a validation step before merging, and non-cash rewards (LINE Points, OPENPOINT, miles) are never silently converted into NT$ cashback.
  • Security scoping: the public endpoint exposes only deterministic query/recommendation tools — no admin tools, no data-reload, no secrets, no customer data; production deployments would restrict origins via ALLOWED_ORIGINS.
